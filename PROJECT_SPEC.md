# PROJECT_SPEC.md

# Техническое задание: веб-приложение TaskerAI

## 1. Цель продукта

Создать локально запускаемое веб-приложение для управления задачами с AI-помощником.

Приложение должно помочь одному пользователю:

- создавать, редактировать и удалять задачи;
- менять статусы задач;
- фильтровать и искать задачи;
- разбивать большие задачи на подзадачи;
- генерировать задачи по цели или описанию;
- улучшать формулировки задач с помощью AI.

Данные должны храниться локально через backend и SQLite. Приложение не требует регистрации и не рассчитано на многопользовательский режим в MVP.

## 2. Границы MVP

В MVP входит:

1. Локальный запуск frontend и backend.
2. Один пользователь без регистрации и авторизации.
3. CRUD для задач.
4. Базовые статусы задач на русском языке: `К выполнению`, `В работе`, `Выполнено`.
5. Системный статус для задач после удаления пользовательского статуса: `Удален статус`.
6. Возможность добавлять, редактировать и удалять пользовательские статусы.
7. Фильтрация задач по статусу, приоритету, дедлайну, тегам и текстовому поиску.
8. Сортировка задач по дате создания, дедлайну, приоритету и статусу.
9. Счетчики задач по статусам.
10. Теги как отдельные сущности со справочником.
11. Подзадачи как отдельные задачи, связанные с материнской задачей, только на один уровень вложенности.
12. Отображение подзадач в материнской задаче как чеклист.
13. Автоматическое зачеркивание подзадачи в чеклисте, если связанная задача переведена в статус `Выполнено`.
14. AI-генерация задач по цели или описанию.
15. AI-разбиение большой задачи на подзадачи.
16. AI-улучшение формулировки задачи.
17. Предпросмотр AI-предложений перед применением.
18. Применение AI-предложений только после подтверждения пользователя.
19. Сохранение истории AI-запросов, AI-ответов и статуса применения предложений.
20. Локальное хранение данных в SQLite.
21. Интеграция с AI через OpenRouter.
22. Настройка AI через Web UI: ввод ключа, валидация ключа, загрузка доступных моделей, выбор модели и сохранение настроек.
23. Хранение OpenRouter-ключа в SQLite без шифрования в MVP.
24. Возможность мокировать OpenRouter API в тестах.

## 3. Целевые пользователи

Основной пользователь MVP - один индивидуальный пользователь, который ведет личные или рабочие задачи локально на своем компьютере.

Потребности пользователя:

- быстро фиксировать задачи;
- видеть актуальный список дел;
- отслеживать прогресс по статусам;
- находить задачи через фильтры и поиск;
- декомпозировать большие задачи;
- получать AI-помощь без автоматического изменения данных.

## 4. Пользовательские сценарии

### 4.1. Создание задачи

1. Пользователь открывает приложение.
2. Нажимает действие создания задачи.
3. Вводит обязательное название задачи.
4. При необходимости заполняет описание, приоритет, дедлайн и теги.
5. Выбирает статус или оставляет статус по умолчанию `К выполнению`.
6. Сохраняет задачу.
7. Задача появляется в списке.

### 4.2. Редактирование задачи

1. Пользователь открывает задачу.
2. Изменяет доступные поля.
3. Сохраняет изменения.
4. Обновленная задача отображается в списке и карточке задачи.

### 4.3. Изменение статуса

1. Пользователь выбирает задачу.
2. Меняет статус на `К выполнению`, `В работе`, `Выполнено` или пользовательский статус.
3. Система сохраняет новый статус.
4. Если задача является подзадачей и получила статус `Выполнено`, она отображается зачеркнутой в чеклисте материнской задачи.

### 4.4. Добавление пользовательского статуса

1. Пользователь открывает управление статусами или форму выбора статуса.
2. Вводит название нового статуса.
3. Система создает пользовательский статус.
4. Новый статус становится доступен для задач и фильтрации.

### 4.5. Редактирование или удаление пользовательского статуса

1. Пользователь открывает управление статусами.
2. Пользователь редактирует название пользовательского статуса или выбирает удаление статуса.
3. При редактировании система сохраняет новое название статуса.
4. При удалении пользовательского статуса система переводит связанные задачи в системный статус `Удален статус`.
5. Базовые системные статусы нельзя удалить.

### 4.6. Фильтрация, сортировка и поиск задач

1. Пользователь открывает список задач.
2. Выбирает фильтры по статусу, приоритету, дедлайну или тегам.
3. При необходимости вводит поисковую строку.
4. При необходимости выбирает сортировку по дате создания, дедлайну, приоритету или статусу.
5. Система показывает только подходящие задачи в выбранном порядке.
6. Пользователь видит счетчики задач по статусам.
7. Пользователь может сбросить фильтры.

### 4.7. Создание подзадачи вручную

1. Пользователь открывает материнскую задачу.
2. Добавляет подзадачу.
3. Система создает отдельную задачу и связывает ее с материнской.
4. Подзадача отображается в материнской задаче как пункт чеклиста.

### 4.8. Удаление задачи

1. Пользователь выбирает удаление задачи.
2. Система показывает подтверждение удаления.
3. Если у задачи нет подзадач, пользователь может подтвердить или отменить удаление.
4. Если у задачи есть подзадачи, пользователь выбирает одно из действий: удалить материнскую задачу вместе с подзадачами, удалить только материнскую задачу и разорвать связь с подзадачами, отменить удаление.
5. Система выполняет выбранное действие только после подтверждения пользователя.

### 4.9. Генерация задач с помощью AI

1. Пользователь вводит цель или описание результата.
2. Отправляет запрос AI-помощнику.
3. Система показывает предложенный список задач.
4. Пользователь подтверждает или отменяет предложения.
5. При подтверждении система создает задачи.
6. При отмене данные не меняются.

### 4.10. Разбиение задачи на подзадачи с помощью AI

1. Пользователь открывает большую задачу.
2. Запускает AI-разбиение.
3. Система показывает предложенный список подзадач.
4. Пользователь подтверждает или отменяет предложения.
5. При подтверждении система создает подзадачи как отдельные задачи и связывает их с материнской задачей.

### 4.11. Улучшение формулировки задачи с помощью AI

1. Пользователь открывает задачу.
2. Запускает AI-улучшение формулировки.
3. Система показывает предложенное название и/или описание.
4. Пользователь подтверждает или отменяет изменение.
5. При подтверждении задача обновляется.

## 5. Функциональные требования

### 5.1. Задачи

1. Система должна позволять создавать задачу.
2. Система должна позволять просматривать список задач.
3. Система должна позволять просматривать одну задачу.
4. Система должна позволять редактировать задачу.
5. Система должна позволять удалять задачу.
6. Система должна позволять менять статус задачи.
7. Обязательные поля задачи: `title`, `status`.
8. Необязательные поля задачи: `description`, `priority`, `deadline`, `tags`.
9. Значения приоритета в MVP: `Низкий`, `Средний`, `Высокий`.
10. Если статус не указан при создании, система должна назначать `К выполнению`.
11. Система должна сохранять задачи в SQLite.
12. Перед удалением задачи система должна запрашивать подтверждение пользователя.
13. При удалении материнской задачи с подзадачами система должна предложить выбор: каскадно удалить подзадачи, удалить только материнскую задачу и разорвать связь с подзадачами, отменить удаление.

### 5.2. Статусы

1. Система должна иметь базовые статусы на русском языке: `К выполнению`, `В работе`, `Выполнено`.
2. Система должна иметь системный статус `Удален статус` для задач, у которых был удален пользовательский статус.
3. Система должна позволять добавлять пользовательские статусы только с названиями на русском языке.
4. Система должна позволять редактировать пользовательские статусы.
5. Система должна позволять удалять пользовательские статусы.
6. При удалении пользовательского статуса система должна переводить связанные задачи в статус `Удален статус`.
7. Система должна позволять назначать пользовательские статусы задачам.
8. Система должна позволять фильтровать задачи по базовым и пользовательским статусам.
9. Система не должна позволять удалять базовые системные статусы.

### 5.3. Фильтры и поиск

1. Система должна поддерживать фильтрацию по статусу.
2. Система должна поддерживать фильтрацию по приоритету.
3. Система должна поддерживать фильтрацию по дедлайну.
4. Система должна поддерживать фильтрацию по тегам.
5. Система должна поддерживать текстовый поиск по названию и описанию.
6. Система должна позволять сбрасывать активные фильтры.
7. Система должна поддерживать сортировку по дате создания, дедлайну, приоритету и статусу.
8. Система должна отображать счетчики задач по статусам.

### 5.4. Теги

1. Система должна хранить теги как отдельные сущности со справочником.
2. Система должна позволять создавать теги в справочнике.
3. Система должна позволять назначать задаче один или несколько тегов из справочника.
4. Система должна позволять фильтровать задачи по тегам из справочника.

### 5.5. Подзадачи

1. Система должна позволять создать подзадачу для материнской задачи.
2. Подзадача должна храниться как отдельная задача.
3. Подзадача должна иметь ссылку на материнскую задачу.
4. Материнская задача должна отображать связанные подзадачи как чеклист.
5. Если подзадача имеет статус `Выполнено`, пункт чеклиста должен быть визуально зачеркнут.
6. Изменение статуса подзадачи должно отражаться в чеклисте материнской задачи.
7. Система должна поддерживать только один уровень вложенности подзадач.
8. Система не должна позволять создавать подзадачи у подзадач.

### 5.6. AI-предложения

1. Система должна показывать AI-результаты как предложения перед применением.
2. Система не должна применять AI-предложения автоматически.
3. Пользователь должен иметь возможность подтвердить AI-предложение.
4. Пользователь должен иметь возможность отменить AI-предложение.
5. При отмене AI-предложения данные не должны изменяться.
6. Система должна сохранять историю AI-запросов и AI-ответов в SQLite.
7. Система должна сохранять статус AI-предложения: `pending`, `applied`, `cancelled`.
8. После подтверждения сохраняется итоговая задача, набор задач или изменение задачи, а запись истории AI-предложения получает статус `applied`.
9. После отмены данные задач не меняются, а запись истории AI-предложения получает статус `cancelled`.

## 6. Нефункциональные требования

### 6.1. Локальный запуск

1. MVP должен запускаться локально на машине разработчика или пользователя.
2. Backend должен работать с локальной SQLite-базой.
3. Приложение не должно требовать внешней базы данных.
4. README на следующих этапах должен содержать команды локального запуска.

### 6.2. Безопасность

1. AI-интеграция должна использовать OpenRouter.
2. API-ключ OpenRouter должен вводиться пользователем через Web UI и валидироваться до сохранения настроек.
3. Валидный API-ключ OpenRouter должен храниться локально в SQLite.
4. Шифрование ключа OpenRouter при локальном хранении не входит в MVP.
5. Реальные API-ключи, токены и секреты не должны храниться в коде или документах.
6. Сохраненный ключ должен отображаться в UI только в маскированном виде и не должен попадать в логи.
7. Пользовательский ввод должен валидироваться до сохранения и перед отправкой в AI.
8. Ошибка OpenRouter API не должна приводить к потере пользовательских данных.
9. Без валидного ключа OpenRouter AI-функции должны быть заблокированы, а базовое управление задачами должно оставаться доступным.

### 6.3. Формат ошибок API

Минимальный формат ошибки backend:

```json
{
  "code": "validation_error",
  "detail": "Человекочитаемое описание ошибки"
}
```

Требования:

1. `code` должен быть стабильным машинным кодом ошибки.
2. `detail` должен быть понятным сообщением для пользователя или frontend.
3. Ошибки валидации должны возвращать HTTP `400` или `422`.
4. Отсутствующие сущности должны возвращать HTTP `404`.
5. Ошибки OpenRouter должны возвращать понятный код ошибки и не раскрывать ключ OpenRouter.

### 6.4. Тестируемость

1. Backend-тесты должны поддерживать сервисно-репозиторную структуру: API tests проверяют HTTP-контракты, service tests проверяют бизнес-правила, repository/integration tests проверяют атомарные операции при необходимости.
2. AI-интеграция должна быть изолирована в сервисном слое, а атомарные вызовы OpenRouter должны быть вынесены в repository/integration layer.
3. OpenRouter API должен мокироваться в тестах.
4. Backend API должен быть пригоден для тестирования через Pytest.
5. Frontend должен быть пригоден для компонентных тестов и E2E smoke-проверок.

### 6.5. Поддерживаемость

1. Frontend, backend, слой хранения данных и AI-интеграция должны быть разделены.
2. Бизнес-логика не должна быть жестко связана с UI.
3. Архитектура не должна мешать добавлению Docker позже.
4. Добавление или замена AI-провайдера не должны требовать переписывания основной логики задач.
5. Backend должен использовать строгую сервисно-репозиторную архитектуру.
6. Endpoint-ы FastAPI должны быть тонким транспортным слоем и не должны содержать SQLAlchemy-запросы, прямые операции с моделями, бизнес-правила или вызовы внешних интеграций.
7. Сервисы должны содержать бизнес-логику: проверки существования, правила изменения/удаления, ограничения вложенности, mock-режимы, подготовку доменных ответов и вызовы репозиториев.
8. Репозитории должны содержать только атомарные операции: запросы к SQLite, сохранение, удаление, массовое обновление или одиночный вызов внешней интеграции, например OpenRouter.

### 6.6. UX

1. Интерфейс должен отображать состояния загрузки, ошибки и пустого списка.
2. Формы должны валидировать обязательные поля.
3. Пользователь должен явно видеть, какие AI-предложения будут применены.
4. Основные сценарии должны быть доступны на desktop и mobile web.

## 7. Модель данных на уровне сущностей

### 7.1. Task

Сущность задачи.

Поля:

- `id` - уникальный идентификатор задачи;
- `title` - обязательное название задачи;
- `description` - необязательное описание;
- `status_id` - ссылка на статус;
- `priority` - необязательный приоритет;
- `deadline` - необязательный дедлайн;
- `parent_task_id` - необязательная ссылка на материнскую задачу;
- `created_at` - дата и время создания;
- `updated_at` - дата и время последнего изменения.

Связи:

- задача принадлежит одному статусу;
- задача может иметь одну материнскую задачу;
- задача может иметь несколько подзадач;
- задача может иметь несколько тегов.

Ограничения:

- `title` - до 120 символов;
- `description` - до 4000 символов;
- `priority` - одно из значений: `Низкий`, `Средний`, `Высокий`;
- вложенность подзадач ограничена одним уровнем.

### 7.2. Status

Сущность статуса задачи.

Поля:

- `id` - уникальный идентификатор статуса;
- `name` - название статуса на русском языке;
- `label` - отображаемое название статуса;
- `is_system` - признак базового статуса;
- `created_at` - дата и время создания.

Базовые статусы:

- `К выполнению`;
- `В работе`;
- `Выполнено`;
- `Удален статус`.

Ограничения:

- пользовательские статусы должны иметь названия на русском языке;
- базовые системные статусы нельзя удалить;
- при удалении пользовательского статуса связанные задачи переводятся в статус `Удален статус`.

### 7.3. Tag

Сущность тега.

Поля:

- `id` - уникальный идентификатор тега;
- `name` - название тега.

Ограничения:

- теги хранятся как отдельные сущности справочника;
- `name` - до 40 символов.

Связи:

- тег может быть связан с несколькими задачами;
- задача может иметь несколько тегов.

### 7.4. TaskTag

Связующая сущность для отношения многие-ко-многим между задачами и тегами.

Поля:

- `task_id` - ссылка на задачу;
- `tag_id` - ссылка на тег.

### 7.5. AiSuggestion

Сущность сохраненного AI-запроса и AI-предложения, которое пользователь может подтвердить или отменить.

Поля зависят от сценария:

- `id` - уникальный идентификатор AI-предложения;
- `type` - тип предложения: `generate_tasks`, `split_task`, `improve_task`;
- `request_text` - исходный пользовательский запрос или текст задачи, отправленный в AI;
- `response_payload` - структурированный ответ OpenRouter с предложенными задачами, подзадачами или улучшенной формулировкой;
- `items` - предложенные задачи или подзадачи, если применимо;
- `title` - предложенное название задачи;
- `description` - предложенное описание задачи;
- `source_task_id` - ссылка на исходную задачу, если предложение связано с существующей задачей;
- `model` - модель OpenRouter, использованная для генерации;
- `status` - статус предложения: `pending`, `applied`, `cancelled`;
- `created_at` - дата и время создания предложения;
- `applied_at` - дата и время применения, если предложение было подтверждено.

Примечание: `AiSuggestion` сохраняется в SQLite, чтобы apply-endpoint-ы могли применять ранее показанные пользователю предложения по идентификатору.

### 7.6. AiSettings

Сущность локальных настроек AI-интеграции.

Поля:

- `id` - уникальный идентификатор записи настроек;
- `provider` - AI-провайдер, для MVP значение `openrouter`;
- `api_key` - сохраненный локально в SQLite ключ OpenRouter;
- `selected_model` - выбранная пользователем модель OpenRouter;
- `is_configured` - признак, что ключ провалидирован и модель выбрана;
- `created_at` - дата и время создания;
- `updated_at` - дата и время последнего изменения.

Примечание: ключ OpenRouter хранится в SQLite без шифрования в MVP. Ключ не должен храниться в репозитории, отображаться в UI целиком или попадать в логи.

## 8. API на уровне endpoint-ов без реализации

### 8.1. Tasks API

`GET /api/tasks`

Получить список задач. Поддерживает query-параметры фильтрации:

- `status`;
- `priority`;
- `deadline_from`;
- `deadline_to`;
- `tag`;
- `search`;
- `parent_task_id`;
- `sort_by` - `created_at`, `deadline`, `priority`, `status`;
- `sort_order` - `asc` или `desc`.

`GET /api/tasks/status-counts`

Получить счетчики задач по статусам.

`POST /api/tasks`

Создать задачу.

`GET /api/tasks/{task_id}`

Получить задачу по идентификатору.

`PATCH /api/tasks/{task_id}`

Частично обновить задачу.

`DELETE /api/tasks/{task_id}`

Удалить задачу. Для материнской задачи с подзадачами поддерживает стратегию `cascade` или `unlink`; отмена удаления выполняется на уровне UI без вызова endpoint-а.

`GET /api/tasks/{task_id}/subtasks`

Получить подзадачи выбранной задачи.

`POST /api/tasks/{task_id}/subtasks`

Создать подзадачу для выбранной задачи.

### 8.2. Statuses API

`GET /api/statuses`

Получить список базовых и пользовательских статусов.

`POST /api/statuses`

Создать пользовательский статус.

`PATCH /api/statuses/{status_id}`

Переименовать пользовательский статус.

`DELETE /api/statuses/{status_id}`

Удалить пользовательский статус и перевести связанные задачи в системный статус `Удален статус`.

### 8.3. Tags API

`GET /api/tags`

Получить список тегов.

`POST /api/tags`

Создать тег.

`PATCH /api/tags/{tag_id}`

Переименовать тег в справочнике.

`DELETE /api/tags/{tag_id}`

Удалить тег из справочника и снять его со связанных задач.

### 8.4. AI API

`GET /api/ai/settings`

Получить текущий статус AI-настроек без раскрытия полного API-ключа.

`POST /api/ai/validate-key`

Проверить ключ OpenRouter, введенный пользователем через Web UI.

`GET /api/ai/models`

Получить список доступных моделей OpenRouter для валидного ключа.

`PUT /api/ai/settings`

Сохранить AI-настройки: провайдер `openrouter`, валидный ключ и выбранную модель.

`POST /api/ai/generate-tasks`

Сгенерировать предложения задач по цели или описанию через выбранную модель OpenRouter. Сохраняет AI-запрос и AI-ответ как `AiSuggestion` со статусом `pending`, но не создает задачи автоматически.

`POST /api/ai/split-task`

Сгенерировать предложения подзадач для существующей или описанной большой задачи через выбранную модель OpenRouter. Сохраняет AI-запрос и AI-ответ как `AiSuggestion` со статусом `pending`, но не создает подзадачи автоматически.

`POST /api/ai/improve-task`

Сгенерировать улучшенную формулировку названия и/или описания задачи через выбранную модель OpenRouter. Сохраняет AI-запрос и AI-ответ как `AiSuggestion` со статусом `pending`, но не обновляет задачу автоматически.

`GET /api/ai/suggestions`

Получить историю AI-предложений с возможностью фильтрации по типу и статусу.

`GET /api/ai/suggestions/{suggestion_id}`

Получить сохраненное AI-предложение по идентификатору.

### 8.5. Apply AI Suggestions API

`POST /api/ai/apply-generated-tasks`

Создать задачи из подтвержденного пользователем AI-предложения по `suggestion_id` и перевести запись истории в статус `applied`.

`POST /api/tasks/{task_id}/apply-ai-subtasks`

Создать подзадачи из подтвержденного пользователем AI-предложения по `suggestion_id`, связать их с материнской задачей и перевести запись истории в статус `applied`.

`PATCH /api/tasks/{task_id}/apply-ai-improvement`

Применить подтвержденную пользователем улучшенную формулировку из AI-предложения по `suggestion_id` к задаче и перевести запись истории в статус `applied`.

`POST /api/ai/suggestions/{suggestion_id}/cancel`

Отменить AI-предложение без изменения задач и перевести запись истории в статус `cancelled`.

## 9. AI-функции

### 9.1. Генерация задач

Вход:

- цель пользователя или текстовое описание результата.

Выход:

- список предложенных задач с названиями;
- опционально описания, приоритеты или теги, если AI вернул их в структурированном виде.

Правила:

- задачи не создаются без подтверждения пользователя;
- пользователь может выбрать, какие задачи применить;
- AI-запрос и AI-ответ сохраняются в истории как `AiSuggestion` со статусом `pending`;
- после подтверждения сохраняются выбранные задачи, а запись истории получает статус `applied`.

Минимальный ожидаемый JSON-ответ AI:

```json
{
  "tasks": [
    {
      "title": "Название задачи",
      "description": "Описание задачи",
      "priority": "Средний",
      "tags": ["тег"]
    }
  ]
}
```

### 9.2. Разбиение задачи на подзадачи

Вход:

- существующая задача или текст большой задачи.

Выход:

- список предложенных подзадач.

Правила:

- подзадачи создаются как отдельные задачи;
- подзадачи связываются с материнской задачей;
- AI-запрос и AI-ответ сохраняются в истории как `AiSuggestion` со статусом `pending`;
- предложения не применяются без подтверждения пользователя;
- после подтверждения запись истории получает статус `applied`.

Минимальный ожидаемый JSON-ответ AI:

```json
{
  "subtasks": [
    {
      "title": "Название подзадачи",
      "description": "Описание подзадачи",
      "priority": "Средний",
      "tags": ["тег"]
    }
  ]
}
```

### 9.3. Улучшение формулировки задачи

Вход:

- текущее название и/или описание задачи.

Выход:

- улучшенное название;
- улучшенное описание, если применимо.

Правила:

- пользователь видит исходную и предложенную формулировку;
- изменение применяется только после подтверждения;
- AI-запрос и AI-ответ сохраняются в истории как `AiSuggestion` со статусом `pending`;
- при подтверждении запись истории получает статус `applied`;
- при отмене задача не меняется, а запись истории получает статус `cancelled`.

Минимальный ожидаемый JSON-ответ AI:

```json
{
  "title": "Улучшенное название задачи",
  "description": "Улучшенное описание задачи"
}
```

### 9.4. Интеграционные требования к AI

1. AI-интеграция в MVP должна выполняться через OpenRouter.
2. Пользователь должен настраивать AI через Web UI.
3. Сначала пользователь вводит ключ OpenRouter.
4. Система должна валидировать ключ до сохранения настроек.
5. После успешной валидации система должна получить список доступных моделей OpenRouter.
6. Пользователь должен выбрать модель из списка доступных моделей.
7. Система должна сохранить валидный ключ и выбранную модель в локальных настройках SQLite.
8. AI-сервис должен быть изолирован от бизнес-логики задач.
9. В тестах OpenRouter API должен заменяться мок-реализацией.
10. Ошибка OpenRouter API должна возвращать понятное сообщение и не блокировать работу с задачами.
11. Пользовательский ввод перед отправкой в AI должен валидироваться.
12. Если ключ OpenRouter отсутствует или невалиден, AI-функции должны быть заблокированы в UI.
13. Ограничение длины AI-запроса в MVP - до 4000 символов.
14. AI-ответ должен соответствовать ожидаемой JSON-схеме сценария; невалидный ответ не должен применяться к задачам.

## 10. Технический стек

Frontend:

- React;
- TypeScript;
- Vite;
- Ant Design (`antd`) как основной UI-фреймворк;
- кастомные стили только точечно, когда возможностей Ant Design недостаточно.

Backend:

- Python;
- FastAPI;
- SQLite;
- Pytest для backend-тестов;
- сервисно-репозиторная архитектура для API, бизнес-логики, хранения и интеграций.

AI-интеграция:

- OpenRouter;
- настройка ключа OpenRouter через Web UI;
- выбор доступной модели OpenRouter через Web UI;
- локальное сохранение AI-настроек в SQLite;
- мок-реализация для тестов.

Тестирование:

- Pytest для backend;
- Vitest для frontend unit/component tests;
- Playwright для E2E smoke-сценариев, когда frontend будет создан.

Контейнеризация:

- Docker и Docker Compose не входят в MVP;
- архитектура должна позволять добавить Docker позже без переработки приложения.

## 11. Ограничения и исключения из MVP

В MVP не входит:

1. Регистрация и авторизация.
2. Многопользовательский режим.
3. Роли и права доступа.
4. Облачное хранение данных.
5. Синхронизация между устройствами.
6. Полноценный аудит всех изменений задач.
7. История изменений задач.
8. Автоматическое применение AI-предложений без подтверждения пользователя.
9. Уведомления по email, push или мессенджерам.
10. Интеграция с календарями.
11. Мобильное приложение.
12. Offline-first режим за пределами локального запуска.
13. Docker-артефакты.
14. Сложная аналитика продуктивности и отчеты.
15. Совместное редактирование задач.

Ограничения:

1. Приложение рассчитано на одного пользователя.
2. Данные хранятся локально в SQLite.
3. AI-функции зависят от доступности OpenRouter и корректного ключа OpenRouter.
4. Без валидного ключа OpenRouter AI-функции должны быть заблокированы, а базовое управление задачами должно оставаться доступным.
5. Ключ OpenRouter хранится в SQLite без шифрования в MVP.

## 12. Риски и открытые вопросы

### 12.1. Риски

1. OpenRouter API может быть недоступен, работать медленно или возвращать некорректный формат ответа.
2. Без строгого формата AI-ответов возможны неоднозначные задачи или подзадачи.
3. Пользовательские статусы усложняют фильтрацию, отображение и перевод задач в статус `Удален статус` при удалении статуса.
4. Связи между задачами и подзадачами требуют аккуратной обработки при удалении задач.
5. Хранение истории AI-запросов и ответов увеличивает объем локальных данных и требует аккуратно не раскрывать ключ OpenRouter в сохраненных payload-ах.
6. Если AI-интеграция не будет изолирована, мокирование OpenRouter и возможная будущая замена AI-провайдера станут сложнее.
7. Если локальная конфигурация будет сделана неаккуратно, последующее добавление Docker может потребовать переработки.

### 12.2. Открытые вопросы

1. Уточнить, нужны ли ограничения на количество задач, тегов и пользовательских статусов в локальной SQLite-базе.

### 12.3. Допущения

1. Поля `description`, `priority`, `deadline` и `tags` являются необязательными.
2. Ответ пользователя "Норм" на вопрос о фильтрах интерпретирован как согласие на фильтры по статусу, приоритету, дедлайну, тегам и текстовому поиску.
3. История AI-запросов и AI-ответов сохраняется только для AI-предложений, без общего аудита всех изменений задач.
4. Подзадачи являются отдельными задачами со связью с материнской задачей.
5. Docker будет добавлен позже и не входит в MVP.
6. Значения приоритета в MVP: `Низкий`, `Средний`, `Высокий`.
7. Базовые статусы в MVP: `К выполнению`, `В работе`, `Выполнено`, `Удален статус`.
