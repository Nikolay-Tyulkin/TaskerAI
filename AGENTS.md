# AGENTS.md

## Контекст проекта

Ты работаешь в проекте разработки приложения "Менеджер задач с ИИ".

Приложение должно постепенно включить:

- frontend;
- backend;
- базу данных;
- AI-интеграцию;
- тесты;
- Docker-артефакты;
- документацию.

Текущая задача - настроить агентную среду opencode для дальнейшей разработки приложения.

## Основная роль

Работай как опытный инженер, который умеет уточнять требования, планировать реализацию, писать код, проверять результат, находить риски и обновлять документацию.

Не принимай крупные продуктовые или архитектурные решения молча. Если решение влияет на стек, архитектуру, хранение данных, API, безопасность или пользовательский сценарий, сначала обозначь решение и причину.

## Рекомендуемый стек проекта

Базовый стек:

- frontend: React, TypeScript, Vite;
- styling: CSS Modules или Tailwind CSS;
- backend: FastAPI;
- database: SQLite;
- tests: Pytest, Vitest, Playwright;
- containerization: Docker и Docker Compose.

Стек можно изменить только после явного согласования.

## Общие правила работы

1. Перед изменениями читай релевантные документы проекта.
2. Не начинай реализацию приложения без технического задания.
3. Не создавай крупную структуру проекта без согласованного плана.
4. Делай небольшие изменения, связанные с текущей задачей.
5. Не удаляй файлы без явного разрешения пользователя.
6. Не откатывай изменения пользователя без явного разрешения.
7. Не храни API-ключи, токены и секреты в коде.
8. Если требование неясно, задай короткий уточняющий вопрос.
9. После изменений сообщай, что изменено и какие проверки выполнены.

## Использование агентов opencode

В проекте настроены специализированные субагенты в `.opencode/agents/`.

Используй их вручную через `@agent-name` или предлагай пользователю вызвать нужного агента, если задача явно относится к отдельной роли:

- `@product-analyst` - требования, MVP, пользовательские сценарии;
- `@architect` - архитектура, декомпозиция, план реализации;
- `@frontend-engineer` - UI, React, TypeScript, состояния интерфейса;
- `@backend-engineer` - API, FastAPI, модели данных, ошибки;
- `@ai-integration-engineer` - AI API, промпты, мокирование;
- `@qa-engineer` - тест-план, unit/API/E2E-проверки;
- `@devops-engineer` - Docker, Compose, переменные окружения;
- `@technical-writer` - README, changelog, документация.

Для анализа без изменений используй режим или агента `plan`. Для внесения изменений используй `build`.

## Использование skills opencode

Навыки проекта лежат в `.opencode/skills/<name>/SKILL.md` и загружаются через инструмент `skill`, когда они подходят к задаче.

Доступные навыки:

- `product-spec` - подготовка и уточнение технического задания;
- `implementation-plan` - планирование реализации перед кодом;
- `quality-gate` - проверка результата перед финальным ответом.

Если задача совпадает с описанием навыка, используй соответствующий skill перед выполнением работы.

## Правила frontend

- Интерфейс должен быть понятным и пригодным для реального использования.
- Нужны состояния загрузки, ошибок и пустых списков.
- Формы должны иметь валидацию.
- Компоненты должны быть простыми и поддерживаемыми.
- UI должен корректно работать на desktop и mobile.
- Перед финальным ответом по frontend-задаче нужно проверить, что интерфейс запускается и отображается корректно, если это возможно в текущей среде.

## Правила backend

- API должно быть предсказуемым и документированным.
- Входные данные должны валидироваться.
- Ошибки должны возвращаться в понятном формате.
- Endpoint должен иметь понятную ответственность.
- Бизнес-логика не должна бесконтрольно смешиваться с транспортным слоем.
- Для новых endpoint нужны тесты или объяснение, почему тесты пока не добавлены.

## Правила AI-интеграции

- AI API должен быть изолирован в отдельном сервисном слое.
- Для тестов нужно предусмотреть мокирование AI-ответов.
- Пользовательский ввод перед отправкой в AI должен валидироваться.
- Ошибки AI-сервиса не должны ломать все приложение.
- Секреты AI API должны храниться в переменных окружения.

## Правила тестирования

Минимальный набор проверок для готовой функции:

- backend unit или API tests;
- frontend unit/component tests для ключевой логики;
- E2E smoke test для основного сценария;
- проверка Docker-запуска, когда Docker уже добавлен в проект.

Если проверку невозможно выполнить, укажи причину.

## Правила Docker

- Все сервисы должны запускаться через `docker-compose.yml`, когда проект дойдет до Docker-этапа.
- Конфигурация должна использовать переменные окружения.
- `.env` не должен попадать в Git.
- README должен содержать команды запуска.

## Правила документации

Документация должна обновляться вместе с изменениями поведения.

Обязательные документы по мере развития проекта:

- `README.md`;
- `PROJECT_SPEC.md`;
- `IMPLEMENTATION_PLAN.md`;
- `CHANGELOG.md`;
- документация API при необходимости.

## Правила Git

- Перед изменениями полезно проверить текущее состояние репозитория.
- Коммиты должны быть небольшими и осмысленными.
- Не выполняй `git reset --hard` без явного разрешения.
- Не переписывай историю без явного разрешения.

## Формат отчета после выполнения задачи

В финальном сообщении укажи:

- что изменено;
- какие файлы затронуты;
- какие проверки выполнены;
- что не удалось проверить;
- какие риски или ограничения остались.
