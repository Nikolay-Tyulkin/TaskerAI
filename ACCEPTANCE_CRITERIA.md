# ACCEPTANCE_CRITERIA.md

# Критерии приемки MVP: "Менеджер задач с ИИ"

## 1. Definition of Done для MVP

MVP считается готовым, если выполнены все обязательные условия:

1. Приложение запускается локально как связка frontend и backend.
2. Backend реализован на FastAPI и использует SQLite для локального хранения данных.
3. Frontend реализован на React, TypeScript, Vite и Ant Design (`antd`).
4. Пользователь может работать без регистрации и авторизации.
5. Пользователь может создавать, просматривать, редактировать и удалять задачи.
6. Задачи сохраняются в SQLite и доступны после перезапуска backend.
7. Базовые статусы доступны на русском языке: `К выполнению`, `В работе`, `Выполнено`.
8. Системный статус `Удален статус` используется для задач после удаления пользовательского статуса.
9. Пользователь может создавать, редактировать и удалять пользовательские статусы.
10. Пользователь может создавать и использовать теги из справочника.
11. Пользователь может фильтровать, искать и сортировать задачи.
12. Пользователь видит счетчики задач по статусам.
13. Пользователь может создавать подзадачи только одного уровня вложенности.
14. Подзадачи отображаются в материнской задаче как чеклист.
15. Подзадача визуально зачеркивается в чеклисте, если ее статус `Выполнено`.
16. Пользователь может удалять материнскую задачу с выбором стратегии: `cascade`, `unlink` или отмена.
17. Пользователь может настроить OpenRouter через Web UI.
18. Без валидного ключа OpenRouter AI-функции заблокированы, а обычная работа с задачами доступна.
19. AI API изолирован так, чтобы тесты не выполняли реальные запросы к OpenRouter.
20. AI-сценарии работают через мок OpenRouter в автоматических тестах.
21. AI-предложения не применяются без подтверждения пользователя.
22. История AI-запросов, AI-ответов и статусов предложений сохраняется в SQLite.
23. Ошибки backend, frontend и AI отображаются пользователю понятным образом.
24. Есть минимальные backend API tests для ключевых сценариев.
25. Есть минимальные frontend component tests для ключевых форм и состояний.
26. E2E smoke test основного пользовательского сценария запланирован на отдельный этап и не обязателен для текущего учебного шага.
27. README содержит команды локального запуска и тестирования.
28. В репозитории нет реальных API-ключей, `.env`, SQLite-баз и других локальных секретов.

## 2. Пользовательские сценарии приемки

### 2.1. Создание задачи

Дано: пользователь открыл приложение.

Когда: пользователь создает задачу с названием.

Тогда:

- задача появляется в списке;
- статус по умолчанию равен `К выполнению`;
- задача сохраняется в SQLite;
- после перезапуска backend задача остается доступной.

### 2.2. Валидация задачи

Дано: пользователь открыл форму задачи.

Когда: пользователь пытается сохранить задачу без названия или с названием длиннее 120 символов.

Тогда:

- задача не сохраняется;
- пользователь видит сообщение об ошибке;
- список задач не меняется.

### 2.3. Редактирование задачи

Дано: задача уже создана.

Когда: пользователь меняет название, описание, приоритет, дедлайн, статус или теги.

Тогда:

- изменения сохраняются;
- список задач и карточка задачи показывают обновленные данные;
- `updated_at` изменяется на backend.

### 2.4. Удаление задачи без подзадач

Дано: задача не имеет подзадач.

Когда: пользователь выбирает удаление и подтверждает действие.

Тогда:

- задача удаляется;
- список задач обновляется;
- при отмене удаления задача остается без изменений.

### 2.5. Удаление материнской задачи с подзадачами

Дано: задача имеет подзадачи.

Когда: пользователь выбирает удаление материнской задачи.

Тогда:

- пользователь видит варианты: удалить вместе с подзадачами, удалить только материнскую задачу и разорвать связь, отменить;
- при выборе `cascade` материнская задача и подзадачи удаляются;
- при выборе `unlink` материнская задача удаляется, подзадачи остаются и теряют связь с материнской задачей;
- при отмене данные не меняются.

### 2.6. Управление статусами

Дано: пользователь открыл управление статусами.

Когда: пользователь создает пользовательский статус на русском языке.

Тогда:

- статус появляется в списке статусов;
- его можно назначить задаче;
- по нему можно фильтровать задачи.

Когда: пользователь редактирует пользовательский статус.

Тогда:

- новое название отображается в списке статусов и у связанных задач.

Когда: пользователь удаляет пользовательский статус.

Тогда:

- связанные задачи переводятся в статус `Удален статус`;
- системные статусы удалить нельзя.

### 2.7. Управление тегами

Дано: пользователь открыл справочник тегов.

Когда: пользователь создает тег.

Тогда:

- тег появляется в справочнике;
- тег можно назначить задаче;
- задачи можно фильтровать по этому тегу.

Когда: пользователь удаляет тег.

Тогда:

- тег удаляется из справочника;
- тег снимается со связанных задач;
- сами задачи не удаляются.

### 2.8. Фильтрация, поиск, сортировка и счетчики

Дано: в системе есть несколько задач с разными статусами, приоритетами, дедлайнами и тегами.

Когда: пользователь применяет фильтры, поиск или сортировку.

Тогда:

- список показывает только подходящие задачи;
- сортировка применяется по выбранному полю;
- сброс фильтров возвращает полный список;
- счетчики по статусам отображаются и обновляются после изменений задач.

### 2.9. Подзадачи

Дано: есть материнская задача.

Когда: пользователь создает подзадачу.

Тогда:

- подзадача создается как отдельная задача;
- подзадача связана с материнской задачей;
- подзадача отображается в материнской задаче как пункт чеклиста.

Когда: пользователь переводит подзадачу в `Выполнено`.

Тогда:

- пункт чеклиста в материнской задаче визуально зачеркивается.

Когда: пользователь пытается создать подзадачу у подзадачи.

Тогда:

- система запрещает действие и показывает понятную ошибку.

### 2.10. Настройка AI

Дано: пользователь открыл AI-настройки.

Когда: пользователь вводит ключ OpenRouter.

Тогда:

- система валидирует ключ через backend;
- при валидном ключе система загружает список доступных моделей;
- пользователь выбирает модель;
- настройки сохраняются в SQLite;
- полный ключ не отображается в UI после сохранения.

Когда: ключ отсутствует или невалиден.

Тогда:

- AI-функции заблокированы;
- базовые функции управления задачами остаются доступными.

### 2.11. AI-генерация задач

Дано: AI-настройки валидны.

Когда: пользователь вводит цель и запускает генерацию задач.

Тогда:

- система показывает предложенный список задач;
- задачи не создаются автоматически;
- AI-запрос и AI-ответ сохраняются как `AiSuggestion` со статусом `pending`;
- при подтверждении выбранные задачи создаются, а предложение получает статус `applied`;
- при отмене задачи не создаются, а предложение получает статус `cancelled`.

### 2.12. AI-разбиение задачи на подзадачи

Дано: есть существующая задача и валидные AI-настройки.

Когда: пользователь запускает AI-разбиение.

Тогда:

- система показывает предложенный список подзадач;
- подзадачи не создаются автоматически;
- AI-предложение сохраняется со статусом `pending`;
- при подтверждении подзадачи создаются как отдельные задачи и связываются с материнской задачей;
- при подтверждении предложение получает статус `applied`;
- при отмене задачи не меняются, предложение получает статус `cancelled`.

### 2.13. AI-улучшение формулировки

Дано: есть существующая задача и валидные AI-настройки.

Когда: пользователь запускает улучшение формулировки.

Тогда:

- пользователь видит исходную и предложенную формулировку;
- задача не обновляется автоматически;
- AI-предложение сохраняется со статусом `pending`;
- при подтверждении задача обновляется, предложение получает статус `applied`;
- при отмене задача не меняется, предложение получает статус `cancelled`.

## 3. API-критерии

### 3.1. Общие API-критерии

1. Все endpoint-ы возвращают JSON.
2. Ошибки возвращаются в понятном формате с HTTP-статусом и человекочитаемым сообщением.
3. Входные данные валидируются на backend.
4. Backend не возвращает полный OpenRouter-ключ ни в одном ответе.
5. Endpoint-ы не требуют регистрации или авторизации в MVP.
6. API tests покрывают успешные и ошибочные сценарии для ключевых endpoint-ов.

### 3.2. Tasks API

Обязательные endpoint-ы:

- `GET /api/tasks`
- `GET /api/tasks/status-counts`
- `POST /api/tasks`
- `GET /api/tasks/{task_id}`
- `PATCH /api/tasks/{task_id}`
- `DELETE /api/tasks/{task_id}`
- `GET /api/tasks/{task_id}/subtasks`
- `POST /api/tasks/{task_id}/subtasks`

Критерии:

1. `POST /api/tasks` создает задачу с валидными данными.
2. `POST /api/tasks` назначает `К выполнению`, если статус не указан.
3. `GET /api/tasks` поддерживает фильтры `status`, `priority`, `deadline_from`, `deadline_to`, `tag`, `search`, `parent_task_id`.
4. `GET /api/tasks` поддерживает `sort_by` со значениями `created_at`, `deadline`, `priority`, `status`.
5. `GET /api/tasks` поддерживает `sort_order` со значениями `asc`, `desc`.
6. `DELETE /api/tasks/{task_id}` поддерживает стратегии `cascade` и `unlink` для материнских задач с подзадачами.
7. `POST /api/tasks/{task_id}/subtasks` запрещает создание подзадачи у подзадачи.

### 3.3. Statuses API

Обязательные endpoint-ы:

- `GET /api/statuses`
- `POST /api/statuses`
- `PATCH /api/statuses/{status_id}`
- `DELETE /api/statuses/{status_id}`

Критерии:

1. Базовые статусы создаются при инициализации системы.
2. Системные статусы нельзя удалить.
3. Пользовательские статусы можно создать, переименовать и удалить.
4. При удалении пользовательского статуса связанные задачи получают статус `Удален статус`.

### 3.4. Tags API

Обязательные endpoint-ы:

- `GET /api/tags`
- `POST /api/tags`
- `PATCH /api/tags/{tag_id}`
- `DELETE /api/tags/{tag_id}`

Критерии:

1. Теги хранятся как отдельные сущности справочника.
2. Тег можно назначить задаче.
3. При удалении тега он снимается со связанных задач.
4. Удаление тега не удаляет задачи.

### 3.5. AI API

Обязательные endpoint-ы:

- `GET /api/ai/settings`
- `POST /api/ai/validate-key`
- `GET /api/ai/models`
- `PUT /api/ai/settings`
- `POST /api/ai/generate-tasks`
- `POST /api/ai/split-task`
- `POST /api/ai/improve-task`
- `GET /api/ai/suggestions`
- `GET /api/ai/suggestions/{suggestion_id}`
- `POST /api/ai/apply-generated-tasks`
- `POST /api/tasks/{task_id}/apply-ai-subtasks`
- `PATCH /api/tasks/{task_id}/apply-ai-improvement`
- `POST /api/ai/suggestions/{suggestion_id}/cancel`

Критерии:

1. `GET /api/ai/settings` не раскрывает полный ключ OpenRouter.
2. `POST /api/ai/validate-key` работает с мок OpenRouter в тестах.
3. `GET /api/ai/models` возвращает список моделей из мока в тестах.
4. AI generation endpoint-ы создают `AiSuggestion` со статусом `pending`.
5. Apply endpoint-ы применяют только предложения со статусом `pending`.
6. Apply endpoint-ы переводят предложение в `applied`.
7. Cancel endpoint переводит предложение в `cancelled` без изменения задач.
8. Повторное применение `applied` или `cancelled` предложения возвращает ошибку.
9. Автоматические тесты не выполняют реальные сетевые запросы к OpenRouter.

## 4. Frontend-критерии

1. UI построен на React, TypeScript, Vite и Ant Design.
2. Основной экран показывает список задач или пустое состояние.
3. UI корректно отображает состояния загрузки, ошибки и успешного сохранения; успешное сохранение подтверждается обновлением данных на экране или уведомлением.
4. Формы создания и редактирования задач валидируют обязательное название.
5. Пользователь может создать, изменить, удалить задачу через UI.
6. Пользователь может изменить статус задачи через UI.
7. Пользователь может управлять пользовательскими статусами через UI.
8. Пользователь может управлять тегами через UI.
9. Пользователь может применять фильтры, поиск и сортировку через UI.
10. Пользователь видит счетчики задач по статусам.
11. Материнская задача отображает подзадачи как чеклист.
12. Выполненная подзадача визуально зачеркнута.
13. UI не позволяет создать подзадачу глубже одного уровня или показывает ошибку backend понятно.
14. При удалении задачи UI показывает подтверждение.
15. При удалении материнской задачи UI показывает выбор `cascade`, `unlink` или отмена.
16. AI-действия заблокированы без валидного ключа OpenRouter.
17. AI-предложения отображаются до применения.
18. Пользователь может подтвердить или отменить AI-предложение.
19. История AI-предложений показывает статусы `pending`, `applied`, `cancelled`.
20. Интерфейс проверен минимум на ширинах `375px` и `1280px`.

## 5. AI-критерии

1. AI-интеграция изолирована в backend service layer, а атомарные вызовы OpenRouter вынесены в repository/integration layer.
2. OpenRouter repository/integration layer имеет мокируемую замену для тестов.
3. Тесты AI не требуют реального OpenRouter-ключа.
4. Тесты AI не выполняют реальные платные API-вызовы.
5. AI-настройки сохраняют валидный ключ и выбранную модель в SQLite.
6. Полный OpenRouter-ключ не отображается в UI после сохранения.
7. AI-запрос ограничен 4000 символами.
8. AI-ответ валидируется перед показом пользователю и перед применением по ожидаемой JSON-схеме сценария из `PROJECT_SPEC.md`.
9. Невалидный AI-ответ не изменяет задачи.
10. Ошибка OpenRouter не блокирует обычную работу с задачами.
11. Генерация задач создает только предложение, а не задачи сразу.
12. Разбиение задачи создает только предложение, а не подзадачи сразу.
13. Улучшение формулировки создает только предложение, а не меняет задачу сразу.
14. Применение AI-предложения требует явного действия пользователя.
15. Отмена AI-предложения не меняет задачи.
16. История AI-предложений сохраняется в SQLite.

## 5.1. Backend-архитектура

1. FastAPI endpoint-ы не содержат SQLAlchemy-запросов, прямых операций с моделями, бизнес-правил или вызовов OpenRouter.
2. Endpoint-ы получают зависимости, вызывают сервисы и возвращают результат.
3. Сервисы содержат бизнес-логику, проверки существования, доменные ошибки, правила удаления и mock-режимы.
4. Репозитории содержат только атомарные операции с SQLite или внешними интеграциями.
5. Backend-тесты разложены по доменам API и сервисной логике.

## 6. Критерии ошибок и пустых состояний

### 6.1. Пустые состояния

1. Если задач нет, frontend показывает понятное пустое состояние и действие создания задачи.
2. Если фильтры не возвращают задач, frontend показывает сообщение, что ничего не найдено, и действие сброса фильтров.
3. Если тегов нет, справочник тегов показывает пустое состояние и действие создания тега.
4. Если пользовательских статусов нет, управление статусами показывает только системные статусы и действие создания статуса.
5. Если AI-история пуста, frontend показывает пустое состояние истории AI-предложений.

### 6.2. Ошибки backend и валидации

Минимальный формат ошибки backend:

```json
{
  "code": "validation_error",
  "detail": "Человекочитаемое описание ошибки"
}
```

1. Пустой `title` возвращает ошибку валидации и не создает задачу.
2. `title` длиннее 120 символов возвращает ошибку валидации.
3. `description` длиннее 4000 символов возвращает ошибку валидации.
4. Невалидный `priority` возвращает ошибку валидации.
5. Создание подзадачи у подзадачи возвращает понятную ошибку.
6. Удаление системного статуса возвращает понятную ошибку.
7. Повторное применение AI-предложения возвращает понятную ошибку.
8. Запрос несуществующей задачи, статуса, тега или AI-предложения возвращает `404`.

### 6.3. Ошибки frontend

1. При ошибке загрузки списка задач пользователь видит сообщение и возможность повторить действие.
2. При ошибке сохранения формы пользователь видит сообщение и введенные данные не теряются.
3. При ошибке удаления пользователь видит сообщение и список обновляется только после успешного ответа backend.
4. При ошибке AI-запроса пользователь видит сообщение, а задачи не меняются.
5. UI не показывает полный OpenRouter-ключ в ошибках, логах или сохраненных сообщениях.

## 7. Минимальные проверки перед финальным ответом агента

Перед финальным ответом по задаче реализации агент должен выполнить минимум:

1. Проверить `git status --short` и назвать затронутые файлы.
2. Просмотреть diff измененных файлов.
3. Убедиться, что не добавлены реальные секреты, `.env` или SQLite-база.
4. Запустить backend tests, если задача затрагивает backend.
5. Запустить frontend tests, если задача затрагивает frontend.
6. Запустить AI tests с мок OpenRouter, если задача затрагивает AI.
7. Запустить E2E smoke test, если задача затрагивает основной пользовательский сценарий и E2E уже настроены.
8. Проверить локальный запуск затронутого сервиса, если это возможно в текущей среде.
9. Обновить документацию, если изменились команды запуска, API-контракты или пользовательское поведение.
10. В финальном ответе указать, что изменено, какие проверки выполнены, что не удалось проверить и какие риски остались.

Если проверку невозможно выполнить, агент должен явно указать причину.

## 8. Что не обязательно на этом этапе

Для MVP не считается обязательным:

1. Регистрация и авторизация.
2. Многопользовательский режим.
3. Роли и права доступа.
4. Облачное хранение данных.
5. Синхронизация между устройствами.
6. Полноценный аудит всех изменений задач.
7. История изменений задач вне истории AI-предложений.
8. Автоматическое применение AI-предложений без подтверждения пользователя.
9. Уведомления по email, push или мессенджерам.
10. Интеграция с календарями.
11. Мобильное приложение.
12. Offline-first режим за пределами локального запуска.
13. Docker-артефакты.
14. Сложная аналитика продуктивности и отчеты.
15. Совместное редактирование задач.
16. Шифрование OpenRouter-ключа в SQLite.
17. Реальные OpenRouter-вызовы в автоматических тестах.
18. Поддержка вложенности подзадач глубже одного уровня.
19. Полная визуальная полировка UI сверх базовой пригодности на Ant Design.
20. Очистка или удаление истории AI-предложений, если отдельное решение об этом еще не принято.
