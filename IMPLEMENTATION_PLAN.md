# IMPLEMENTATION_PLAN.md

# План реализации: веб-приложение TaskerAI

## 1. Цель плана

Реализовать MVP из `PROJECT_SPEC.md` инкрементально: сначала устойчивый backend и модель данных, затем frontend для управления задачами, после этого AI-интеграция через OpenRouter, история AI-предложений и E2E-проверки.

План не предполагает создание Docker-артефактов в MVP, но структура проекта должна позволять добавить Docker позже без переработки приложения.

Backend реализуется строго по сервисно-репозиторной архитектуре. Endpoint-ы вызывают только сервисы. Сервисы содержат бизнес-логику и правила домена. Репозитории содержат только атомарные операции с SQLite или внешними интеграциями, включая одиночные обращения к OpenRouter.

### Этап 2. Backend: задачи, статусы, теги, фильтрация и сортировка

Цель: реализовать основной API управления задачами без AI.

Основные задачи:

Подэтап 2A. Базовые задачи и статусы:

1. Реализовать `Tasks API`: список, создание, получение, обновление, удаление.
2. Реализовать `Statuses API`: список, создание, переименование, удаление пользовательского статуса.
3. При удалении пользовательского статуса переводить связанные задачи в `Удален статус`.
4. Валидировать пользовательские статусы как русскоязычные названия.

Подэтап 2B. Теги, фильтры и списки:

1. Реализовать `Tags API`: список, создание, переименование, удаление тега.
2. Реализовать связь задач и тегов.
3. Реализовать фильтры по статусу, приоритету, дедлайну, тегам и текстовому поиску.
4. Реализовать сортировку по `created_at`, `deadline`, `priority`, `status`.
5. Реализовать счетчики задач по статусам.

Подэтап 2C. Подзадачи и удаление:

1. Реализовать подзадачи одного уровня и запрет подзадач у подзадач.
2. Реализовать удаление материнской задачи со стратегиями `cascade` и `unlink`.

Предполагаемые файлы и модули:

- `backend/app/api/routes_tasks.py`
- `backend/app/api/routes_statuses.py`
- `backend/app/api/routes_tags.py`
- `backend/app/services/task_service.py`
- `backend/app/services/status_service.py`
- `backend/app/services/tag_service.py`
- `backend/app/repositories/task_repository.py`
- `backend/app/repositories/status_repository.py`
- `backend/app/repositories/tag_repository.py`
- `backend/app/core/errors.py`
- `backend/tests/test_tasks_api.py`
- `backend/tests/test_statuses_api.py`
- `backend/tests/test_tags_api.py`

Проверки:

1. Создание задачи без статуса назначает `К выполнению`.
2. Валидация `title` до 120 символов и `description` до 4000 символов.
3. Приоритет принимает только `Низкий`, `Средний`, `Высокий`.
4. Пользовательский статус создается, редактируется и удаляется.
5. Пользовательский статус с нерусскоязычным названием отклоняется валидацией.
6. При удалении пользовательского статуса связанные задачи получают `Удален статус`.
7. Системные статусы нельзя удалить.
8. Теги создаются как справочник и назначаются задачам.
9. Фильтры, поиск, сортировка и счетчики возвращают ожидаемые данные.
10. Подзадачу нельзя создать у подзадачи.
11. Удаление материнской задачи работает со стратегиями `cascade` и `unlink`.

Зависимости:

- Зависит от этапа 1.
- Блокирует полноценную frontend-реализацию задач.
- AI apply-flow зависит от этого этапа.

### Этап 5. Backend: AI-предложения, история и применение

Цель: реализовать генерацию AI-предложений, сохранение истории и применение подтвержденных предложений.

Основные задачи:

1. Реализовать `POST /api/ai/generate-tasks`.
2. Реализовать `POST /api/ai/split-task`.
3. Реализовать `POST /api/ai/improve-task`.
4. Сохранять AI-запрос и структурированный AI-ответ как `AiSuggestion` со статусом `pending`.
5. Реализовать `GET /api/ai/suggestions` и `GET /api/ai/suggestions/{suggestion_id}`.
6. Реализовать `POST /api/ai/apply-generated-tasks` по `suggestion_id`.
7. Реализовать `POST /api/tasks/{task_id}/apply-ai-subtasks` по `suggestion_id`.
8. Реализовать `PATCH /api/tasks/{task_id}/apply-ai-improvement` по `suggestion_id`.
9. Реализовать `POST /api/ai/suggestions/{suggestion_id}/cancel`.
10. Защититься от повторного применения уже `applied` или `cancelled` предложения.

Предполагаемые файлы и модули:

- `backend/app/api/routes_ai.py`
- `backend/app/services/ai_service.py`
- `backend/app/services/tasks_service.py`
- `backend/app/schemas/ai.py`
- `backend/tests/test_ai_api.py`
- `backend/tests/test_tasks_api.py`

Проверки:

1. Каждый AI endpoint создает `AiSuggestion` со статусом `pending`.
2. История AI-предложений фильтруется по типу и статусу.
3. Apply generated tasks создает задачи и меняет статус предложения на `applied`.
4. Apply subtasks создает подзадачи только одного уровня и меняет статус предложения на `applied`.
5. Apply improvement обновляет задачу и меняет статус предложения на `applied`.
6. Cancel меняет статус предложения на `cancelled` и не меняет задачи.
7. Повторное применение `applied` или `cancelled` предложения возвращает понятную ошибку.
8. Все AI-тесты используют мок OpenRouter и не требуют реального API-ключа.

Зависимости:

- Нужен до frontend AI UI.

## 9. Риски и способы снижения

### Риск 1. MVP слишком большой для учебного проекта

Снижение:

- Реализовывать строго по этапам.
- Не начинать AI UI до готового backend задач.
- Если сроки ограничены, сначала отложить редактирование тегов, E2E AI history UI или сложные состояния управления статусами.

### Риск 2. Хранение OpenRouter-ключа в SQLite без шифрования

Снижение:

- Не коммитить SQLite-базу.
- Добавить SQLite-файлы и `.env` в `.gitignore`.
- Не возвращать полный ключ из API.
- Маскировать ключ в UI.
- Не логировать request body для AI settings.

### Риск 3. Реальные затраты на AI API в тестах

Снижение:

- Ввести mock OpenRouter-клиент до реализации AI-сценариев.
- Запретить реальные сетевые вызовы в automated tests.
- Использовать стабильные fixture-ответы для генерации задач, подзадач и улучшения формулировки.

### Риск 4. Неоднозначный формат AI-ответов

Снижение:

- Требовать структурированный JSON-ответ от AI-сервиса.
- Валидировать AI-ответ Pydantic-схемами.
- При невалидном ответе сохранять ошибку и показывать понятное сообщение, не изменяя задачи.

### Риск 5. Сложная логика подзадач и удаления

Снижение:

- Ограничить вложенность одним уровнем на backend и frontend.
- Покрыть стратегию `cascade` и `unlink` API-тестами.
- Не выполнять удаление материнской задачи без явной стратегии.

### Риск 6. Пользовательские статусы усложняют данные

Снижение:

- Разделить системные статусы и пользовательские статусы через `is_system`.
- Запретить удаление системных статусов.
- При удалении пользовательского статуса всегда переводить задачи в `Удален статус`.

### Риск 7. Frontend и backend расходятся по контрактам

Снижение:

- Сначала реализовать и протестировать backend schemas.
- Синхронизировать frontend types с backend contract.
- Для спорных endpoint-ов добавить примеры request/response в README или API notes.

## 10. Решения, требующие подтверждения

1. Решить, нужны ли лимиты количества задач, тегов, пользовательских статусов и AI-истории в SQLite.
2. Уточнить точный формат request body для apply endpoint-ов: минимально нужен `suggestion_id`, опционально список выбранных item-ов из предложения.
3. Уточнить, нужен ли endpoint для удаления или очистки AI-истории, так как история теперь сохраняется в SQLite.
