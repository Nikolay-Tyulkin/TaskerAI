# Feature Spec: Kanban Board

## Цель

Добавить канбан-доску как альтернативное представление существующих задач Task, чтобы пользователь мог видеть и менять состояние задач по колонкам статусов без перехода на отдельную модель данных.

## Контекст и проблема

В MVP задачи доступны в виде списка. Такой формат удобен для линейного просмотра, но хуже показывает распределение задач по рабочему процессу. Канбан-доска должна дать пользователю визуальное представление тех же задач по статусам и сохранить совместимость с текущим списком задач.

## Целевые пользователи

- Пользователь TaskerAI, который управляет личными задачами.
- Пользователь, которому нужно быстро оценить, какие задачи находятся в каждом статусе.
- Пользователь, который хочет менять статус задачи из визуального board view.

## Пользовательские сценарии

1. Пользователь открывает экран задач и видит доступное переключение между list view и board view.
2. Пользователь выбирает board view и видит канбан-доску с колонками статусов.
3. Пользователь видит, что существующие задачи распределены по колонкам согласно их текущему статусу.
4. Пользователь меняет статус задачи из board view, и эта же задача обновляется в общей сущности Task.
5. Пользователь возвращается в list view и видит актуальные данные задач после изменений на доске.
6. Пользователь обновляет страницу или повторно открывает экран задач и сохраняет доступ к обоим представлениям.

## Функциональные требования

- Канбан-доска использует существующую сущность `Task`.
- Отдельная сущность `KanbanTask` не создается.
- Board view отображает те же задачи, что и list view.
- Задачи распределяются по колонкам на основе поля статуса существующей задачи.
- Переключение между list view и board view должно быть доступно на экране задач.
- Переключение представления не должно создавать, удалять или дублировать задачи.
- Смена статуса из board view должна обновлять ту же задачу, которая отображается в list view.
- Если задач нет, board view должен показывать понятное пустое состояние.
- Если загрузка или обновление задач завершается ошибкой, board view должен показывать понятное состояние ошибки.

## Нефункциональные требования

- Интерфейс должен корректно работать на desktop и mobile.
- Board view не должен ломать существующий list view.
- Изменения должны быть минимальными и не должны вводить новую доменную модель без необходимости.
- Поведение API должно оставаться предсказуемым и совместимым с текущей сущностью Task.
- Тесты существующего MVP должны продолжать проходить.

## Вне scope

- Создание отдельной сущности `KanbanTask`.
- Создание отдельной таблицы или коллекции для канбан-задач.
- Полноценная настройка кастомных колонок пользователем.
- Изменение набора статусов без отдельного согласования.
- Drag-and-drop, если для смены статуса достаточно другого простого UI-механизма на первом этапе.
- Массовые операции с задачами на доске.
- Фильтры, поиск и сортировка специально для board view, если они не входят в уже существующее поведение списка.
- AI-функции для доски.
- Изменения Docker-инфраструктуры, если текущий Docker-запуск уже поддерживает приложение.

## Зависимости и ограничения

- Фича зависит от текущей модели `Task`, ее поля статуса и существующих операций чтения и обновления задач.
- Если текущий API уже поддерживает обновление статуса Task, отдельный backend endpoint не нужен.
- Если текущий API не поддерживает обновление статуса, потребуется минимальное расширение существующего API Task без введения новой сущности.
- Набор колонок должен соответствовать существующим статусам задач.
- Перед реализацией нужно сверить фактическую структуру frontend, backend и тестов в репозитории.

## Открытые вопросы

- Какие статусы Task уже зафиксированы в MVP и в каком порядке они должны отображаться на доске?
- Нужно ли сохранять выбранное представление пользователя между сессиями или достаточно локального состояния на экране?
- Нужен ли drag-and-drop в первой версии или достаточно кнопок/селекта для смены статуса?
- Должны ли существующие фильтры или сортировка списка применяться к board view, если они уже есть?

## Риски и допущения

- Допущение: у существующей сущности `Task` уже есть статус или эквивалентное поле, пригодное для колонок.
- Риск: если в MVP нет операции обновления статуса, потребуется backend-изменение и дополнительные API-тесты.
- Риск: drag-and-drop может увеличить сложность реализации и тестирования, поэтому его нужно подтверждать отдельно.
- Риск: различия между list view и board view могут привести к рассинхронизации UI, если оба представления не используют один источник данных.
