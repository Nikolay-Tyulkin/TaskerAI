# Implementation Plan: Kanban Board

## Предпосылки

- Фича реализуется после релиза `0.1.0 MVP` в ветке `feature/kanban-board`.
- Код приложения на этапе создания этих артефактов не меняется.
- Канбан-доска использует существующую сущность `Task`.
- Отдельная сущность `KanbanTask` не создается.
- Перед началом реализации нужно прочитать текущие спецификации проекта, структуру frontend, backend и тестов.

## Этапы реализации

1. Изучить текущую модель `Task`, статусы задач, API чтения и обновления задач.
2. Изучить текущий экран списка задач и способ загрузки данных во frontend.
3. Зафиксировать фактический набор колонок board view на основе существующих статусов Task.
4. Добавить состояние переключения между list view и board view на экране задач.
5. Реализовать компонент board view, который группирует существующие Task по статусам.
6. Реализовать UI смены статуса задачи из board view через существующий механизм обновления Task.
7. Проверить, что list view использует обновленные данные после изменений на доске.
8. Добавить или обновить тесты для переключения представлений и изменения статуса.
9. Выполнить проверки перед merge.
10. Обновить документацию, если поведение пользователя или команды запуска изменятся.

## Frontend-изменения

- Найти текущий экран или компонент списка задач.
- Добавить переключатель `list view` / `board view` без удаления существующего списка.
- Создать простой компонент канбан-доски, который принимает массив существующих `Task`.
- Сгруппировать задачи по существующим статусам.
- Отобразить колонки статусов и карточки задач.
- Добавить пустое состояние для доски без задач.
- Добавить состояние загрузки и ошибки, если они уже используются на экране задач.
- Добавить действие смены статуса из карточки или колонки доски.
- Убедиться, что после смены статуса обновляется общий источник данных, а не локальная копия только для доски.
- Проверить адаптивность desktop и mobile.

## Backend-изменения

- Если существующий backend уже позволяет читать задачи и обновлять статус `Task`, backend-изменения не нужны.
- Если обновление статуса не поддерживается, добавить минимальное расширение существующего API Task.
- Endpoint должен оставаться тонким транспортным слоем.
- Бизнес-логика изменения статуса должна находиться в service layer.
- Операции хранения должны находиться в repository layer.
- Новая сущность, таблица или модель `KanbanTask` не создается.

## Предполагаемые файлы и модули

- Frontend: текущий экран задач, компонент списка задач, новый или существующий компонент board view, стили компонента.
- Backend: существующие роуты, сервисы и репозитории Task только при необходимости расширения обновления статуса.
- Tests: frontend unit/component tests, backend API/service tests при backend-изменениях, E2E smoke test основного сценария.
- Docs: README или пользовательская документация только если изменятся команды запуска или описание пользовательского поведения.

## Зависимости между задачами

- Нельзя реализовать board view до подтверждения фактических статусов `Task`.
- Переключение представлений зависит от текущего экрана списка задач.
- Смена статуса из board view зависит от существующего или нового API обновления Task.
- E2E smoke test зависит от готовых frontend- и backend-изменений.

## Проверки по этапам

- После изучения модели: подтвердить, что используется существующая сущность `Task`.
- После реализации переключателя: проверить, что list view продолжает отображаться как раньше.
- После реализации board view: проверить распределение задач по колонкам статусов.
- После реализации смены статуса: проверить, что статус меняется у той же задачи и отражается в list view.
- После тестов: запустить релевантные backend, frontend и E2E проверки.

## Тесты

- Frontend unit/component test: board view отображает колонки статусов.
- Frontend unit/component test: задачи распределяются по колонкам согласно статусу.
- Frontend unit/component test: переключение list view / board view работает.
- Frontend unit/component test: действие смены статуса вызывает обновление существующей Task.
- Backend API/service tests: добавить только если потребуется новый или измененный backend endpoint.
- E2E smoke test: пользователь открывает задачи, переключается на доску, меняет статус, возвращается в список и видит обновленную задачу.
- Regression tests: существующие тесты списка задач должны продолжать проходить.

## Проверки перед merge

- Проверить `git status`, чтобы в merge не попали лишние файлы.
- Запустить backend tests, если backend существует и затронут.
- Запустить frontend tests, если frontend существует и затронут.
- Запустить E2E smoke test основного сценария, если Playwright уже настроен.
- Проверить Docker-запуск или хотя бы релевантную Docker-команду, если Docker уже настроен в проекте.
- Проверить приложение вручную на desktop и mobile viewport.
- Проверить, что не созданы `KanbanTask`, отдельная таблица или отдельное хранилище для задач доски.

## Миграции и данные

- Миграции не ожидаются, если существующая сущность `Task` уже содержит статус.
- Если статус Task отсутствует, это меняет scope и требует отдельного согласования до реализации.
- Данные задач не должны дублироваться для board view.

## Документация

- Документация запуска не меняется, если команды запуска остаются прежними.
- Пользовательскую документацию нужно обновить, если в проекте уже есть описание режима работы со списком задач.
- Changelog нужно обновить при завершении реализации фичи.

## Риски реализации

- Неочевидный набор статусов может привести к неправильным колонкам.
- Локальное состояние board view может рассинхронизироваться со списком задач.
- Drag-and-drop может потребовать дополнительных зависимостей и усложнить mobile UX.
- Docker-проверка может быть недоступна, если Docker не установлен или не запущен в среде.

## Решения, требующие подтверждения

- Точный набор и порядок колонок.
- Нужен ли drag-and-drop в первой версии.
- Нужно ли сохранять выбранное представление между сессиями.
- Нужно ли применять существующие фильтры и сортировку списка к board view.
